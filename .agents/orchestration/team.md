# 팀 역할과 소유

## lead (Opus)
- 하는 일: 계획, 일 나누기, 결과 통합
  - 사용자 요청을 request.md 에 원문 그대로 고정하고 plan.md(또는 prd·sdd)를 쓴다
  - TASKS.md 에 작업 · 담당 · 잡은 파일을 적어 배정한다
  - 작업을 나눌 때 builder(구현)와 test(테스트)로 나눠 큐에 넣고 순서를 조율한다 (테스트 먼저 → 구현 → 확인). 단계별 커밋은 그대로 — 테스트 커밋은 test, 구현 커밋은 builder
  - 담당에게는 request.md 경로를 넘긴다 (요약해서 넘기지 않는다)
  - test 의 게이트 판정을 [verdict.md "게이트 판정 규칙"](verdict.md) 대로 확인하고 PR 을 연다. PR 뒤에는 CI `gate` 결과를 같은 규칙으로 확인한 뒤에만 "확인 끝" · "통과"라고 쓴다 (미리보기 빌드 통과만 보고 통과라고 쓰지 않는다)
- 고칠 수 있는 곳: .agents/specs/, .agents/orchestration/TASKS.md

## builder (구현)
- 하는 일: lead가 배정한 plan 대로 기능을 만든다 (화면 · API · 수집 · 공용 로직)
  - 구현만 한다. 테스트 실행(단위 · e2e · 게이트 · 미리보기 확인 캡처)은 하지 않는다 — 모두 test 의 일
  - 구현을 마치면 커밋 · 푸시하고 lead 에게 보고한다 (확인은 test 가 이어받음)
- 고칠 수 있는 곳:
  - apps/web/src/** (GEO 소유 파일 제외)
  - apps/api/src/** (GEO 소유 파일 제외)
  - packages/shared/src/** · packages/ui/src/**
  - apps/api/drizzle/migrations/ 에 새 마이그레이션 추가 (기존 파일 수정은 금지)
  - docs/domain/** (규칙이 바뀌면 함께 갱신)
- 고치면 안 되는 곳: 테스트 파일, 보호 파일
  - 테스트 파일: *.test.ts · *.test.tsx · apps/web/e2e/** · apps/web/e2e-responsive/**
  - 보호 파일: .agents/protected.txt 목록 (DB 스키마 · wrangler 설정 · next.config · 워크플로 등)

## test (테스트)
- 하는 일: 테스트에 관한 일은 전부 맡는다
  - 구현보다 먼저 테스트 작성(FAIL 확인) — "테스트 먼저" 커밋은 test 가 한다
  - request.md 원문의 요구마다 테스트를 하나 이상 만든다
  - 구현이 끝나면 단위 테스트 · e2e · 게이트(`bash .agents/checks.sh`)를 실행해 PASS 를 확인한다 — 판정은 [verdict.md "게이트 판정 규칙"](verdict.md) 대로 (로그 전체에서 ❌ 0개 · 끝 몇 줄만 보고 판정 금지)
  - 미리보기 1280 · 390 확인과 시안 비교 캡처도 test 가 한다
  - 결과를 lead에게 보고한다
  - 빌드 · e2e 는 꼭 필요할 때만 실행한다 (D1 하루 읽기 한도)
- 고칠 수 있는 곳:
  - 소스 옆의 *.test.ts · *.test.tsx
  - apps/web/e2e/** · apps/web/e2e-responsive/**
  - 테스트용 데이터 (fixture)
- 주의: FAIL 단계의 게이트 실패는 정상. 구현하지 말고 보고하고 멈춤

## geo
- 하는 일: 검색 노출 · AI 답변 측정 · 봇 방문 분석 · 알리기
  - robots · sitemap · 메타데이터 · 구조화 데이터 관리
  - 매일 AI 답변 세션 측정 → apps/api/data/geo-answers/YYYY-MM-DD.json
  - 검색 노출 조사 (#157) 결과 정리 · 매일 댓글
  - 바깥 링크 후보 찾기: 사이트를 소개할 만한 곳 목록과 이유 (지금 다른 사이트에서 넘어온 방문 0)
  - 이름 알리기: "Flapfx"를 검색하면 다른 것(암호화폐 토큰 등)이 나옴 → 이름과 사이트를 이어 줄 소개 글 초안
  - 매일 알림 글 · 광고 소재 초안 하나: 그날 사이트 자료(이번 주 가장 싼 도착지 · 항공권 출발일 최저가 · 환율 위치)로 문구와 이미지 안을 만든다. Meta(인스타그램 · 페이스북) 광고에 쓸 것 — 형식 · 크기 · 문구 길이는 사용자 답(11-20)이 아래다.
    - 올리는 종류: "둘 다" — 매일 일반 게시물을 올리고, 반응이 좋은 것만 골라 유료로 민다.
    - 계정: "아직 없음" — 인스타그램 · 페이스북 페이지 · 광고 계정은 사용자가 만든다. 팀은 계정을 만들거나 로그인하지 않는다.
    - 올리는 사람: "팀이 초안, 내가 올림" — geo 는 초안까지. 올리기 · 예산 · 유료 전환은 사용자가 한다.
    - 소재: "이미지 한 장".
    - 매일 초안 한 묶음: `docs/marketing/YYYY-MM-DD/` 에 이미지 한 장 + 문구(본문 · 해시태그 · 이미지 대체 글) + 쓴 숫자와 받은 날짜 + 눌렀을 때 갈 주소(flapfx.com 의 해당 페이지).
    - 이미지: 세로 4:5 (1080×1350) 한 장. 사이트 토큰(파랑 #2438A8 · 남색 #16246E · 노랑 #F7C548 · 글자판 · 탑승권 모양)을 쓰고 사진은 쓰지 않는다. 그날 숫자 하나를 크게.
    - 유료로 밀 후보는 geo 가 고르지 않는다. 사용자가 반응을 보고 정한다.
    - 계정이 만들어지기 전에도 초안은 매일 쌓는다(사용자가 계정을 만든 뒤 골라 올림).
  - 일일 기록을 만드는 날에는 #157 댓글과 그날 초안을 함께 낸다
- 지킬 것
  - 바깥에 올리지 않는다. 글 · 광고를 올리고 돈을 쓰는 일은 사용자가 승인한 뒤 사용자 계정으로 한다. 에이전트는 초안과 목록까지만.
  - 숫자는 그날 사이트 · 공개 API 에 있는 값만 쓴다. 지어내지 않는다. 받은 날짜를 함께 적는다.
  - "오를 것 · 내릴 것" 같은 예측 · 투자 권유 문구를 쓰지 않는다 (사이트 원칙: 예측 아님).
  - 자료 제공처 설명(구글 항공권 · SerpApi 등)을 문구에 넣지 않는다 (11-20 사용자 결정).
  - 공개 저장소다. 계정 · 예산 · 내부 절차는 저장소에 적지 않는다.
- 고칠 수 있는 곳:
  - apps/web/src/app/robots.ts · apps/web/src/app/sitemap.ts
  - apps/web/src/app/geo/** · apps/web/src/features/geo/**
  - apps/web/src/bff/track-visit.ts · packages/shared/src/domain/geo-visit.ts
  - apps/api/src/features/geo/** · apps/api/scripts/geo-ask.ts · apps/api/scripts/gsc-sync.ts
  - apps/api/data/geo-answers/** · docs/geo-measurement.md
  - docs/marketing/** (초안 · 후보 목록 · 날짜별 폴더)
- 범위 밖이 필요하면: lead에게 제안 (예: layout.tsx 의 메타데이터 · 페이지 본문 문구)

## data (데이터 지킴이 · 세션 이름 dev-data@hav · 모델 sonnet)
- 왜: 수집원이 환율 · 과세환율 · 물가지표 · 항공권으로 늘었는데 실패 · 이상 값을 알아채는 자리가 없다. #128(수출입은행 수집 실패 영업일 4일)이 늦게 잡혔고, 11-20 에는 항공권 가격이 0건인 채 머지된 것을 사용자가 먼저 봤다.
- 하는 일
  - 작업한 날마다 수집 상태 점검: 자료마다 "마지막으로 받은 날 · 줄 수 · 빠진 것"
    - 환율(평일) · 과세환율(주) · 물가지표 KOSIS · ECOS(월) · 세계은행 물가(연) · 항공권 출발일 가격(월 · 수 · 금 · 8개 공항 × 약 42일)
  - 값이 이상한지 보기: 빈 값 · 전날과 지나치게 다른 값 · 공항 · 통화 누락 · 날짜가 멈춤
  - 예약 실행 결과 보기: GitHub Actions(수집 · 다시 빌드 · API 배포) 성공 여부
  - 바깥 API 한도 보기: SerpApi 무료 월 250회 대비 이번 달 예상 사용량(코드상 계산 · 실제 남은 횟수는 확인 가능할 때만)
  - 결과를 일일 기록 이슈 "오늘 상태"에 넣을 수 있게 lead 에게 보고. 실패 · 이상이면 이슈 초안과 원인 후보를 낸다.
  - 새 수집이 머지될 때 "첫 수집이 언제 도는지 · 그 전 화면은 어떻게 보이는지"를 lead 에게 미리 알린다.
- 지킬 것
  - 운영 D1 을 직접 조회하지 않는다(하루 읽기 한도). 공개 API 응답과 워크플로 결과로 본다. 빌드를 돌리지 않는다.
  - 운영 수집을 손으로 다시 돌리지 않는다. 필요하면 lead 를 거쳐 사용자에게 알린다.
  - 받지 못한 값은 "없음"으로 적는다. 채워 넣지 않는다. 키 값은 어디에도 쓰지 않는다.
  - 수집 코드를 직접 고치지 않는다. 고칠 것은 lead 에게 요청(구현은 builder · 테스트는 test).
- 고칠 수 있는 곳: docs/data-health.md (점검 방법 · 자료별 기준 · 기록)

## 공통
- 커밋·PR:
  - 1작업 = 1브랜치 (task/NNNN-이름). 각자 자기 범위 파일만 그 브랜치에 커밋한다
  - PR 은 lead만 연다. 제목은 "작업 NNNN: 요약", 버그 · 보안 수정은 "작업 NNNN: 패치(버그|보안) — 요약"
  - 담당자는 kyungchan3007 로 지정한다
  - 머지는 사람이 "머지해" 한 뒤에만 한다. harness-approved 라벨은 붙이지 않는다
  - 완료는 checks.sh PASS 일 때만 말한다. "통과"의 기준은 [verdict.md "게이트 판정 규칙"](verdict.md) 하나다 (로컬 로그 전체 ❌ 0개 + PR 이면 최신 커밋 CI gate=SUCCESS). 비밀값은 코드 · 로그 · 커밋에 쓰지 않는다
- PR · 이슈 본문 · 댓글에는 팀 내부 절차 문장을 쓰지 않는다 (게이트 결과 한 줄만) — 11-20 사용자 지적
- 남의 범위를 바꿔야 하면: 직접 고치지 말고 lead에게 요청
- 부탁받은 범위만 하고, 끝나면 보고하고 멈춤
- 사용자에게 보이는 글은 모두 한국어
