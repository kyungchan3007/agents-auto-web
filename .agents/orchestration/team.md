# 팀 역할과 소유

## lead (Opus)
- 하는 일: 계획, 일 나누기, 결과 통합
  - 사용자 요청을 request.md 에 원문 그대로 고정하고 plan.md(또는 prd·sdd)를 쓴다
  - TASKS.md 에 작업 · 담당 · 잡은 파일을 적어 배정한다
  - 작업을 나눌 때 builder(구현)와 test(테스트)로 나눠 큐에 넣고 순서를 조율한다 (테스트 먼저 → 구현 → 확인). 단계별 커밋은 그대로 — 테스트 커밋은 test, 구현 커밋은 builder
  - 담당에게는 request.md 경로를 넘긴다 (요약해서 넘기지 않는다)
  - builder 지시에 확인 일(빌드 · 단위 테스트 · e2e · 화면 비교)을 넣지 않는다 — builder 가 하는 확인은 푸시 전 타입 검사와 바꾼 파일의 lint 뿐이고, 나머지는 test 의 일이다 (2026-11-22 재발 방지)
  - test 의 보고(로컬에서 무엇을 돌렸는지)를 확인하고 PR 을 연다. PR 뒤에는 최신 커밋의 CI `gate` 결과를 [verdict.md "게이트 판정 규칙"](verdict.md) 대로 확인한 뒤에만 "확인 끝" · "통과"라고 쓴다 (미리보기 빌드 통과만 보고 통과라고 쓰지 않는다)
  - 브랜치 흐름(작업 0244): main(운영) · develop(모으는 곳) · task/NNNN(develop 에서 땀). 작업 폴더와 브랜치는 origin/develop 에서 만들고, PR 의 base 는 develop 이다(급한 버그 같은 예외만 main). e2e 는 PR 의 대상에 따라 다르다: develop 은 CI e2e 없음(build 까지 · 로컬은 바꾼 spec 만 · 작업 0295), main 은 전체(넓은 화면 + 휴대폰).
  - lead 가 여는 PR 이 둘 더 있다: 하루 마무리 PR(develop → main · fast-forward · 전체 e2e)과 data · geo 반영 PR(그날 자료 커밋만 cherry-pick → main). 머지는 사람이 "머지해" 한 뒤에만 한다.
  - 디자인 PR(작업 0246 · [verdict.md "디자인 PR 판정"](verdict.md)): 화면만 바꾸는 작업이면 PR 을 **열 때** `design` 라벨을 단다(`gh pr create --label design` · 나중에 달면 다음 푸시부터 반영). 동작을 바꾸는 변경에는 달지 않는다. PR 본문에 "디자인 테스트 실패 N개"를 한 줄로 적고, 미리보기 주소와 볼 경로를 사용자에게 준다. 팀 안에서 모양을 맞추는 왕복은 하지 않는다 — 모양은 사용자가 미리보기에서 보고, 고칠 곳을 말하면 그때 고친다.
  - 하루 마무리 PR 의 `design` 라벨은 그날 머지된 PR 이 모두 design 일 때만 단다. 본문에는 그날 바뀐 화면 목록(페이지 · 무엇이 바뀌었는지 한 줄씩) · 미리보기 주소 · "미뤄 둔 디자인 테스트 N개" 한 줄(기한 알림은 두지 않음)을 적는다.
  - 새 자료를 받는 작업(수집 · 새 API)은 PR 본문과 사용자 회신 맨 위에 쓴다: "운영에 자료가 생기기 전까지 미리보기 · 운영에 빈 상태로 보입니다. 첫 수집: 언제" + 고정 자료로 본 비교 캡처 경로. data 의 "첫 수집 미리 알림"과 같은 내용을 lead 회신에도 넣는다.
  - 작업 묶음 하나가 끝나면 자리를 새로 연다는 규칙을 지킨다. 새로 여는 일은 claude-desktop 이 하고, lead 는 "묶음 끝"을 알린다.
- 고칠 수 있는 곳: .agents/specs/, .agents/orchestration/TASKS.md

## builder (구현)
- 하는 일: lead가 배정한 plan 대로 기능을 만든다 (화면 · API · 수집 · 공용 로직)
  - 구현만 한다. 테스트 실행(단위 · e2e · 게이트 · 미리보기 확인 캡처)은 하지 않는다 — 모두 test 의 일
  - 단, 푸시 전에 타입 검사(바꾼 패키지에서 `npm run typecheck` · apps/web 은 `next typegen && tsc --noEmit`)와 이번에 바꾼 파일의 lint 는 builder 가 직접 돌린다. 바뀐 파일 목록만 eslint 에 넘기고 `--fix` 도 그 파일에만 쓴다 (2026-11-22 사용자 결정). 통과하면 커밋 · 푸시하고, 실패하면 고친 뒤 푸시한다
  - 테스트 파일(*.test.ts · *.test.tsx · apps/web/e2e/** · apps/web/e2e-responsive/**)의 lint 는 test 가 한다 — builder 는 테스트 파일 lint 결과를 test 에게 넘기지 않는다
  - 구현을 마치면 커밋 · 푸시하고 lead 에게 보고한다. 보고에 "타입 검사 · lint(바꾼 파일) 통과" 한 줄을 적는다 (그 밖의 확인은 test 가 이어받음)
  - 작업 폴더(worktree)와 브랜치는 origin/develop 에서 만든다 (작업 0244)
  - 디자인 PR 이어도 구현만 한다(작업 0246). 모양을 맞추려고 팀 안에서 왕복하지 않는다. 동작(lib · hooks · API)을 함께 바꾸게 되면 lead 에게 알려 `design` 라벨을 달지 않게 한다.
  - 같은 공용 파일 끝에 덧붙이지 않는다. 화면 스타일은 기능 폴더 안 파일이나 tokens.css 에 둔다. globals.css 끝에 이어 쓰지 않는다.

## test (테스트)
- 하는 일: 테스트에 관한 일은 전부 맡는다
  - 전체 빌드 · 단위 · e2e · 하네스 · gate · 미리보기 확인 · 테스트 작성 · 테스트 파일 lint 는 모두 test 의 일이다 (builder 는 푸시 전 타입 검사와 바꾼 파일의 lint 만 한다)
  - 구현보다 먼저 테스트 작성(FAIL 확인) — "테스트 먼저" 커밋은 test 가 한다
  - 새 테스트를 쓸지는 작업 종류로 정한다(작업 0297 · 사용자 결정 — 모양만 바뀌는 작업에 테스트를 쓰느라 시간을 씀):
    - 색 · 모서리 · 투명도 · 그림자 · 테두리처럼 보이는 값만 바뀌는 작업, 그리고 문구(글자)를 바꾸거나 지우는 작업(작업 0301 · 사용자 결정): 새 테스트를 쓰지 않는다. 바꾼 spec 이 없으니 로컬 e2e 도 없다. 확인은 CI(타입 검사 · lint · 단위 · build)와 사용자의 미리보기.
    - 크기 · 간격 · 위치 · 줄바꿈이 바뀌는 작업: 새 테스트를 쓰지 않는다. 이미 있는 기능 테스트(넘침 없음 · 밀림 없음 · 누르는 자리 44px · 초점 고리 등)가 main 으로 가는 PR 의 전체 e2e 에서 돈다. 깨진 기존 테스트가 있으면 그때 고친다.
    - 숫자 · 동작이 바뀌거나, 사용자가 새 조건("밀리지 않는다" · "넘치지 않는다" 같은)을 붙인 작업: 그 요구마다 기능 테스트를 하나 이상 새로 쓴다.
    - lead 는 작업을 나눌 때 위 셋 중 무엇인지 적어 test 에게 넘긴다. 애매하면 앞의 것(테스트를 덜 쓰는 쪽)으로 본다.
  - 구현이 끝나면 로컬에서는 바뀐 곳 · 실패한 곳만 돌려 확인한다 — 판정은 [verdict.md "게이트 판정 규칙"](verdict.md) 대로 (최신 커밋의 CI gate)
  - 미리보기 1280 · 390 확인과 시안 비교 캡처도 test 가 한다 (디자인 PR 은 제외 — 아래)
  - 결과를 lead에게 보고한다
  - 빌드 · e2e 는 꼭 필요할 때만 실행한다 (D1 하루 읽기 한도)
  - 테스트는 두 종류다(작업 0246 · [verdict.md "디자인 PR 판정"](verdict.md)). 기능 테스트(표시 없음)는 늘 막고, 디자인 테스트(이름에 `@design`)는 좌표 · 여백 · 색 · 글꼴 · 모서리 · 그림자 · 배치 순서 · 정렬 · 움직임의 시작과 끝 모양처럼 정해 둔 값을 본다. 한 테스트에 둘을 섞지 않고(섞였으면 둘로 나눔) 헷갈리면 표시하지 않는다. "첫 화면에 들어온다" · "가로로 넘치지 않는다" · "값이 바뀌어도 밀리지 않는다"처럼 사용자가 정한 조건은 기능 테스트로 둔다(조건 자체를 사용자가 바꿀 때만 고침). 630개를 전부 분류하지 않고, 디자인 작업에서 깨질 때마다 표시한다.
  - 디자인 PR 이면 기능 테스트가 깨졌을 때만 움직인다. 디자인 테스트는 고치지 않고 시안 비교 캡처도 하지 않는다. `@design` 표시가 빠진 것을 발견하면 표시만 붙인다. 실패한 디자인 테스트는 `docs/design-tests-pending.md` 에 쌓는다.
  - 로컬 전체 e2e · 로컬 전체 게이트는 돌리지 않는다. 전체 e2e 는 하루 마무리 PR(대상 main)에서 CI 가 본다. (작업 0244)
    - 훅이 실행 전에 막는다(`.agents/scripts/e2e-guard.mjs` · 작업 0294 · 0295): spec 없는 로컬 e2e · 이 작업에서 바꾸지 않은 spec · spec 이름이 아닌 걸러내기 인자 · Full 작업의 로컬 checks.sh. 막히면 이유와 돌릴 수 있는 spec 목록이 나온다. 지시(lead)로 범위를 넓히지 않는다.
    - 푸시 전 로컬: 단위 · typecheck · lint 전체 + **이 작업에서 새로 쓰거나 고친 spec 파일만**(작업 0295 · 사용자 결정 — 연결표로 고르면 20 ~ 30개 · 테스트 200 ~ 300개라 오래 걸림). 바꾼 spec 이 없으면 로컬 e2e 는 없다. 전체 e2e 실패는 main 으로 가는 PR 에서 그 spec 만 로컬에서 고친다.
    - CI(PR 대상 develop)는 e2e 를 돌리지 않는다 — build 까지만(작업 0295). 문서 · 하네스 · 자료 · rigs 만 바뀌면 build 도 없음. 전체 e2e(넓은 화면 + 휴대폰)는 main 으로 가는 PR 에서만 돈다.
    - 새 기능 · 새 spec 은 연결표(.agents/e2e-map.json) 한 줄까지가 작업이다(하네스 검사가 봄 · main PR 의 전체 e2e 와 앞으로의 고르기에 씀).
- 고칠 수 있는 곳:
  - 소스 옆의 *.test.ts · *.test.tsx
  - apps/web/e2e/** · apps/web/e2e-responsive/** · apps/admin/e2e/** (작업 0312)
  - 테스트용 데이터 (fixture)
- 주의: FAIL 단계의 게이트 실패는 정상. 구현하지 말고 보고하고 멈춤

## data (데이터 지킴이 · 세션 이름 dev-data@hav · 모델 sonnet)
