## 정책 (사용자와 정한 것 · 이대로 구현하고 문서에 적는다)

### 1. 테스트는 두 종류다
- **기능 테스트** — 표시 없음. 항상 막는다.
  - 페이지가 열리고 오류가 없는지 · 계산 결과 · 검색 · 통화나 도시 바꾸기 · 받은 숫자가 그대로 나오고 없으면 빈 값인지 · 키보드 · 화면 읽기 도구
  - **사용자가 정한 조건:** "첫 화면에 들어온다"(0217) · "가로로 넘치지 않는다" · "값이 바뀌어도 밀리지 않는다"(0208 · 넓은 화면) 같은 것. 모양 검사처럼 보여도 기능 테스트로 둔다. 조건 자체를 사용자가 바꾸기로 했을 때만 고친다.
- **디자인 테스트** — 테스트 이름에 `@design` 표시.
  - 좌표 · 여백 · 색 · 글꼴 · 모서리 · 그림자처럼 정해 둔 값이 그대로인지 · 요소의 배치 순서 · 정렬 · 움직임의 시작과 끝 모양
- 한 테스트에 둘을 섞지 않는다(섞여 있으면 둘로 나눈다). 헷갈리면 표시하지 않는다(기능 테스트로 둠 — 막는 쪽이 안전한 쪽).
- **이번 작업에서 표시할 범위는 좁게:** 거의 모양만 보는 파일(예: home-fix-0217 의 값 검사 · home-pill · home-design · calc-gap · light-only · tokens · fonts · *-design)과 0245 에서 깨졌던 테스트부터. 나머지는 이후 디자인 작업에서 깨질 때마다 표시한다. 630개를 전부 분류하지 않는다(시간 · 토큰).
- 단위 테스트 중 스타일 클래스 이름을 검사하는 것(약 15개)도 같은 기준으로 표시한다(표시 방법은 builder · test 가 정함 — 예: 테스트 이름에 `@design`).

### 2. 디자인 PR 의 조건 — 라벨 **그리고** 파일
- PR 에 `design` 라벨이 있고, 바뀐 파일이 모두 "화면 쪽"일 때만 디자인 PR.
- 화면 쪽 = 화면 부품(`apps/web/src/features/*/components/**` · `apps/web/src/app/**` 의 page · layout 화면 코드 · `packages/ui/src/components/**`) · 스타일(`*.css` · `packages/ui/src/tokens.css`) · 테스트 파일 · 작업 기록(`.agents/specs/**`) · 문서. 정확한 목록은 구현하면서 정하되 **허용 목록 방식**(목록에 없으면 평소 PR)으로.
- 계산 · 판정 로직(`lib/`) · 화면 동작(`hooks/`) · API(`apps/api/**`) · 공용 도메인(`packages/shared/**`) · 수집 · 설정 · 하네스가 하나라도 섞이면 평소 PR. 이때 "design 라벨인데 이 파일이 섞였다"는 경고 줄을 낸다.
- 라벨 없음 → 파일이 화면 쪽뿐이어도 평소 PR.
- `design` 라벨은 **lead 가 단다**. 동작을 바꾸는 변경에는 달지 않는다.

### 3. 게이트
| PR 종류 | 기능 테스트 | 디자인 테스트(`@design`) |
| --- | --- | --- |
| 평소 PR | 실패하면 막음 | 실패하면 막음 |
| 디자인 PR | 실패하면 막음 | 돌리되 막지 않고 실패 목록만 남김 |
| 하루 마무리 PR(develop → main) — 그날 디자인 PR 뿐 | 실패하면 막음 | 돌리되 막지 않고 목록만 남김 |
| 하루 마무리 PR — 평소 PR 이 하나라도 섞임 | 실패하면 막음 | 실패하면 막음 |
- 디자인 테스트를 끄지 않는다. 돌려서 무엇이 달라졌는지 목록으로 남긴다(로그에 한 묶음 · "막지 않음"이 분명히 보이게).
- 하루 마무리 PR 이 "디자인 PR 뿐"인지 가려내는 방법은 구현에서 정한다(예: develop → main 사이 머지된 PR 들의 라벨 · 또는 그 구간에 바뀐 파일이 허용 목록 안인지). 가려내지 못하면 평소 규칙(막음)으로 떨어지게 한다.
- 디자인 PR 에서도 e2e 고르기(연결표 · develop 은 고른 spec · main 은 전체)는 지금 그대로다. 달라지는 것은 `@design` 테스트의 실패가 막느냐뿐이다.
- 하네스 자체 테스트(`harness.test.mjs`)에 위 표의 네 경우와 "라벨 있음 + 다른 파일 섞임 → 평소 + 경고"를 더한다.

### 4. 팀의 역할 (디자인 PR 일 때)
- builder: 구현만 한다.
- test: 기능 테스트가 깨졌을 때만 움직인다. 디자인 테스트는 고치지 않고, 시안 비교 캡처도 하지 않는다. `@design` 표시가 빠진 것을 발견하면 표시만 붙인다.
- lead: `design` 라벨을 달고 PR 을 연다. 본문에 "디자인 테스트 실패 N개"를 한 줄로 적는다. 미리보기 주소와 볼 경로를 사용자에게 준다.
- 팀 안에서 모양을 맞추는 왕복은 하지 않는다. 모양은 사용자가 미리보기에서 직접 보고, 고칠 곳을 말하면 그때 고친다.

### 5. 하루 마무리 PR 본문
- 그날 바뀐 화면 목록(페이지 · 무엇이 바뀌었는지 한 줄씩)과 미리보기 주소.
- "미뤄 둔 디자인 테스트 N개" 한 줄(기한 알림은 두지 않음).

### 6. 미뤄 둔 디자인 테스트
- 실패 목록은 `docs/design-tests-pending.md` 한 파일에 쌓는다(어느 테스트 · 어느 작업에서 · 무엇이 달라졌는지). 맨 위에 이 파일이 무엇이고 언제 비우는지 세 줄.
- AI 티 걷어 내기가 끝나면 작업 한 건으로 정리한다. 이때 전부 되살리지 않고 **크게 깨지는 것만 잡도록 줄인다**.
  - 남길 것: 요소가 겹치지 않는지 · 화면 밖으로 나가지 않는지 · 주요 구역이 보이는지
  - 없앨 것: 여백 · 좌표 · 색 · 모서리의 정확한 값을 고정하는 검사
- (정리 작업 자체는 이번 범위가 아니다. 규칙만 적는다.)
