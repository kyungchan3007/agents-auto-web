# PRD — 무엇을 · 왜

> 원문(request.md)을 옮긴 파생 문서. 요구 충족 판정 기준은 언제나 원문이다. 정책 원본은 [handoff.md](handoff.md) "정책" 1~7.

## 문제
- 디자인만 바꿔도 모양을 고정해 둔 테스트가 깨져 test 고침 → builder 다시 맞춤 왕복이 생긴다(0245: 커밋 8개 중 디자인 수정 3개).
- 사용자가 걱정하는 것은 토큰과 시간 비용이다. 모양은 사용자가 미리보기에서 직접 본다.
- AI 티 걷어 내기 1차 17건 · 2차 · 3차가 모두 디자인 변경이라 같은 왕복이 계속된다.

## 목표
1. 테스트가 두 종류로 갈린다: 기능 테스트(표시 없음 · 늘 막음) · 디자인 테스트(이름에 `@design`).
2. 게이트가 "디자인 PR"(design 라벨 **그리고** 바뀐 파일이 모두 화면 쪽 허용 목록 안)을 알아보고, 그때 `@design` 실패는 막지 않고 목록으로만 남긴다. 기능 테스트는 늘 막는다.
3. 라벨이 있는데 화면 쪽 밖 파일이 섞이면 평소 PR + 경고 줄. 라벨이 없으면 평소 PR. 가려내지 못하면 평소(막음).
4. 하루 마무리 PR(develop → main)도 같은 규칙: 그날 디자인 PR 뿐이면 `@design` 은 목록만, 평소 PR 이 섞이면 막음.
5. 규칙이 문서에 있다: AGENTS.md 한 줄 · verdict.md "디자인 PR 판정" · team.md 역할(lead · builder · test) · rig 템플릿 안내문 · docs/design-tests-pending.md(새 파일).
6. 이번 작업에서 `@design` 표시는 좁게: 거의 모양만 보는 파일과 0245 에서 깨졌던 테스트, 스타일 클래스 이름을 보는 단위 테스트(약 15개).

## 비목표
- AI 티 1차 17건 구현 · 디자인 테스트 줄이기 정리 작업 · e2e 연결표 구조 변경.
- 화면 코드 변경(테스트 이름에 표시 · 테스트 둘로 나누기만).
- 630개 테스트 전부 분류.
- `.github/workflows/**` 변경(아래 결정 참고).

## 애매한 곳
- 하루 마무리 PR 이 "디자인 PR 뿐"인지 가르는 방법 → (가정 · lead 결정) 하루 마무리 PR 에도 같은 "라벨 + 파일" 규칙을 쓴다. lead 는 그날 develop 에 머지된 PR 이 모두 design 라벨일 때만 하루 마무리 PR 에 design 라벨을 달고, 게이트는 main...develop 구간 바뀐 파일이 모두 허용 목록 안인지 다시 본다. GitHub API 를 부르지 않아 워크플로 · 토큰을 건드리지 않는다. 라벨을 잘못 달아도 파일 검사가 막는다(하네스 · API · lib 등이 섞이면 평소).
- 라벨을 읽는 곳 → (가정) 워크플로는 그대로 두고 checks.sh 가 `GITHUB_EVENT_PATH` 의 `pull_request.labels` 를 읽는다. 지금 워크플로는 harness-approved 외 라벨 이벤트로는 게이트를 다시 돌리지 않으므로, **design 라벨은 PR 을 열 때 단다**(`gh pr create --label design`). 나중에 달았으면 다음 푸시(또는 harness-approved 이벤트)부터 반영된다 — team.md 에 적는다.
- 단위 테스트(vitest)에서 `@design` 을 막지 않는 방법 → builder 가 정한다(예: 디자인 PR 일 때 `-t` 로 두 번 나눠 돌리기). 조건: 기능 단위 테스트는 늘 막고, `@design` 단위 실패는 목록만.
